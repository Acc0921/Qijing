# 设计原则

## Clean-room 产品边界

栖境是按第一版目标重新定义的信息架构、交互和实现，不是旧应用换名称、换颜色或重新排版后的套壳。

公开工程只描述新产品的目标、协议和行为，不携带旧应用的包名、资源、页面命名、数据库表名、脚本格式、视觉资产或品牌文案。历史解析资料仅用于内部确认功能覆盖，不作为页面、数据或代码实现模板。

以下行为不符合 clean-room 边界：

- 按旧页面建立一一对应的新页面，只替换标题、图标或主题色。
- 复用旧脚本入口、旧数据字段或旧模块层级作为产品导航。
- 在公开文档、代码注释、测试数据或截图中暴露旧产品标识。
- 把底层参数列表直接搬到 UI，让用户重新面对旧式工具菜单。

## 产品信息架构

第一版采用五个稳定的顶层目的地。底部导航表达用户任务，不直接映射平台层 C0-C5，也不为每项底层能力建立独立入口。

| 顶层入口 | 对应范围 | 用户要完成的任务 |
| --- | --- | --- |
| 总览 | M1、C0/C1/C4 状态摘要 | 判断设备是否就绪、当前后端和自动化是否正常，并查看最近结果 |
| 应用 | M2 | 找到目标应用，并从应用上下文进入场景创建 |
| 场景 | M3 | 创建、编辑、启停和理解自动化规则 |
| 调节 | M4 + M5 | 先观察 CPU/内存/ZRAM，再预览和执行受支持的调节 |
| 监控 | M8 | 开始采集、观察指标、结束会话并回看或导出 |

五栏在手机主界面保持同级、稳定顺序和清晰选中态。二级功能使用页面内分段、页签或任务跳转，不继续扩张底部导航。入口显示用户语言“总览、应用、场景、调节、监控”，模块编号只用于工程追踪，不应压过任务名称。

## 用户任务路径

设计和测试以端到端任务是否完成为准，不以“页面能打开”或“接口已存在”为完成条件。

1. **首次就绪**：打开总览 → 看到设备与后端状态 → 理解缺少权限的影响 → 主动授权 → 返回后状态刷新。
2. **为应用创建场景**：应用 → 搜索/筛选 → 选择应用 → 自动带入场景编辑 → 保存并启用 → 在场景页看到作用范围。
3. **安全手动调节**：调节 → 读取当前值与支持范围 → 修改目标 → 查看变更预览 → 危险操作确认 → 应用并读回 → 查看恢复与日志。
4. **验证体验变化**：监控 → 开始当前窗口采集 → 查看采集范围和实时指标 → 停止 → 查看摘要、历史或导出 CSV。
5. **处理异常**：任何任务失败 → 在当前上下文看到原因和恢复结果 → 可进入最近任务查看完整记录，而不是只收到短暂提示。

跨栏跳转必须保留上下文。例如从“应用”进入“场景”时携带包名，从“总览”进入“调节”时保留当前后端认知；返回后不得要求用户重复搜索或重新理解状态。

### 场景链路工作台

M3 采用已确认的方案 A“场景链路工作台”，把场景从参数表单升级为一条可解释的任务链：**应用 → 意图 → 优先级 → 预演 → 启用 → 命中 → 恢复**。用户在启用前能看到冲突、能力和恢复条件，运行时能理解为何命中，离场后能核对是否恢复。

工作台严格区分保存、预演和真实启用；dry-run 命中不产生“已生效”语义。第一版场景继承全局执行方式，全局方式变化会停用场景并要求重新预演，不能静默升级真实权限。完整组件、状态机、当前能力和未来边界见 [方案 A：场景链路工作台](scene-chain-workbench.md)。

## 交互与视觉原则

对知乎等成熟内容产品的学习只提炼通用方法：稳定的底部导航、清楚的标题—摘要—操作层级、渐进披露、列表可扫读和及时状态反馈。栖境将这些方法转换为设备工具的任务路径，不复制其他产品的源码、资源、品牌配色、专有文案或页面组合。

1. **先结论后细节**：首屏先回答“当前状态、能否操作、下一步是什么”，原始路径和底层参数放在次级信息中。
2. **一屏一个主任务**：主要按钮与当前页面目标一致；次要动作使用较低视觉权重，避免工具按钮墙。
3. **渐进披露**：普通用户先看到状态、推荐范围和影响，高级参数在明确展开后出现。
4. **状态不靠猜测**：加载、空内容、无权限、不支持、执行中、成功、失败、恢复中和恢复失败均有独立文案。
5. **信息卡服务于分组**：卡片用于聚合一个决策所需的信息，不为每个数值单独套卡，也不堆叠无意义阴影。
6. **新视觉语言**：Compose + Material 3、自有色板、排版、圆角和状态组件；不复刻旧版页面结构，也不以传统 XML 表单作为视觉模板。

### Android 原生工具页面语法

- 全局采用 edge-to-edge、紧凑 Top App Bar、稳定底部导航和 Android 返回层级；权限入口明确跳转系统设置并在返回后刷新。
- 普通状态使用分组标题、整行可点击的 `ListItem`、分隔线和背景层级；卡片只用于场景链路、变化预演、任务轨迹和监测图表等确实需要独立边界的对象。
- 执行方式、任务筛选等多选项使用 Bottom Sheet 渐进披露；高风险写入使用预演后的确认 Sheet，保留明确标准按钮。
- 首屏不放营销眉题、问候语、产品宣言或大型 Hero。页面标题保持 20–28sp，常规圆角以 8/12/16dp 为主，每屏原则上只有一个高权重主动作。
- 栖境的品牌识别来自就绪状态、场景链路、变化预演、验证/恢复语义与薄荷绿状态色，不依赖网页式渐变、胶囊和嵌套指标卡。

### 观感与数据表达语言

- 页面以冷静的灰绿背景承载白色/深灰成组表面，边界主要来自背景层级、细分隔线和最多 1dp 的轻阴影；圆角只包裹一个状态组、场景对象、调节决策或监测会话。
- 总览、应用、场景、调节、监控分别使用薄荷、紫、蓝、橙、玫红作为弱功能标记；安全结果仍使用统一的成功、警告、失败语义，不能用页面装饰色替代状态判断。
- 设备数据优先组织为共享指标带、连续列表和策略域分组，避免每个数值单独成卡；技术细节保留在支持文本和详情层，结论、当前值与可执行动作保持可扫读。
- 标题在常规字体下保持明确但不占满首屏；系统字体放大时隐藏非必要副标题、允许状态核心纵向重排，主动作和风险文案不得被裁切。
- 视觉参考只用于提炼密度、层次和节奏。界面不得展示探测不到的指标、伪造 Root 就绪、暗示 GPU/ZRAM 可写，或把预演描述为已经应用。

## 危险操作确认

确认强度按风险分级，避免所有按钮都弹窗，也避免真实系统写入一键触发。

| 等级 | 示例 | 交互要求 |
| --- | --- | --- |
| 低风险 | 浏览状态、搜索应用、保存未启用场景、CSV 分享 | 直接执行，提供明确结果；不得滥用确认框 |
| 中风险 | Usage Stats/Shizuku 权限、启动只读监控或自动化服务 | 操作前就地说明用途、范围和拒绝后的降级行为，由用户主动触发系统授权 |
| 高风险 | Root/Shizuku 真实 CPU 或 swappiness 写入、启用会自动写入的场景 | 必须先预览，再进行二次确认；执行中防重复点击；结束后读回验证并展示恢复入口/策略 |

高风险确认必须显示：实际后端、受影响能力、原值、目标值、作用时机、恢复触发条件和主要风险。主按钮使用“确认并应用”等具体动词，不使用含糊的“确定”。快照不完整、能力未验证或恢复命令不可生成时，确认按钮必须禁用。

ZRAM 重建、任意 shell 和未建立恢复策略的厂商专用写入不因增加确认框而变得安全，第一版继续关闭。

## 可访问性基线

- 所有可点击目标至少 `48 × 48 dp`；图标按钮提供可读名称，装饰图标不重复朗读。
- 导航、开关、页签、对话框和执行状态提供正确语义、选中/禁用状态与合理 TalkBack 顺序。
- 成功、警告、失败和后端状态同时使用文字或图标，不只依赖颜色。
- 正文与背景对比度至少 4.5:1，大号文字和必要图形至少 3:1；亮色与深色主题分别检查。
- 系统字体放大至 200% 时，核心任务不截断、不重叠，允许换行和滚动；小屏不得隐藏主要操作。
- 动效不承载唯一信息，并尊重系统动画缩放；执行中状态即使没有动画也可理解。
- 错误信息说明发生了什么、是否已恢复以及用户下一步，不只显示错误码。

## 实现原则

1. **意图优先**：UI 提交 `CpuIntent`、`MemoryIntent` 和 `SceneProfile`，不拼接 shell 字符串。
2. **能力驱动**：先探测设备能力，再决定可用操作；厂商差异收敛在 adapter，而不是散落在页面。
3. **事务可回滚**：每次场景应用都有 task id、执行日志、原值快照和 rollback command。
4. **数据与执行解耦**：C3 只保存业务意图和遥测，C0 负责把意图转换为设备操作。
5. **安全默认值**：真实特权后端必须显式选择；未完成能力探测与真机验收的写入保持关闭。
6. **可验证反馈**：成功必须来自实际读回结果，dry-run 只能称为“预览”，不能显示“已应用”。

## 公开仓库禁入项

- 旧 APK、反编译产物、旧数据库或旧配置文件。
- 旧应用包名、旧接口地址、旧脚本路径和旧品牌文案。
- 未经授权的第三方资源、在线脚本或厂商专用二进制。
