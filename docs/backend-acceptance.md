# 后端与恢复验收标准

本文定义 C0 特权后端、C1 恢复生命周期以及真机验证的发布验收条件。任一后端只有在对应条目全部通过后，才可在 UI 中标记为“可用”；检测到可执行文件、服务进程或 Binder 并不等于具备某项写入能力。

## 1. 通用安全约束

### 1.1 命令边界

- UI、场景数据和导入数据只能生成结构化 `CapabilityCommand`，不得传入任意 shell 文本。
- 每个可写 capability 必须映射到代码内固定的命令模板、参数类型、取值范围、目标路径和对应的只读验证器。
- capability 不在白名单、参数缺失、参数越界、路径未探测或后端能力不足时，必须返回 `Unsupported` 或带稳定错误码的 `Failed`，且不得执行部分命令。
- 用户输入不得参与 shell 操作符、重定向目标或路径拼接。日志不得记录授权令牌、完整私有路径或其他敏感信息。

### 1.2 选择与授权

- UI 必须展示当前实际后端、授权状态、支持的能力及不可用原因。
- 后端选择必须可预测；不得在写入失败后静默切换到权限更高的后端。
- 自动化服务处于 `RUNNING`、`STOPPING` 或 `RECOVERY_REQUIRED` 时不得切换后端；只有恢复完成并持久标记为 `STOPPED` 后才能选择新的执行方式。
- 授权拒绝、授权撤销、进程/Binder 死亡和超时必须终止当前任务，释放资源并写入结构化日志。
- dry-run 只能显示预览，不能产生“已应用”的用户反馈。

### 1.3 事务与验证

每次场景应用必须按以下顺序执行：

1. 校验全部 command 和后端能力。
2. 读取全部目标的原值并建立快照；任何原值无法读取时，不开始写入。
3. 按计划写入，每一步均检查退出状态并读取系统值验证。
4. 任一步失败时，按已成功写入的逆序执行恢复，并再次读取验证。
5. 只有全部目标读回值符合预期后，任务才可标记为 `Applied`。

同一时间只允许一个调节事务。重复应用同一场景必须幂等，不得覆盖最初用于离场恢复的快照。

## 2. Root 后端验收

- 能区分“未安装 su”“请求被拒绝”“授权可用”“执行超时”和“命令失败”。
- 授权只在用户触发需要 Root 的操作时申请；只读页面不得主动弹出 Root 授权。
- 所有写入均通过 capability 白名单生成，不提供任意命令终端。
- Root 会话退出、进程被杀或授权被撤销后，后续任务安全失败，UI 和能力矩阵同步更新。
- 在有 Root 和无 Root 的设备上分别覆盖：授权允许、拒绝、永久拒绝/撤销、超时、目标路径不存在、目标只读、写入成功、读回不一致、恢复成功、恢复失败。

## 3. Shizuku 后端验收

- 接入 Shizuku SDK，能区分“服务未运行”“未授权”“已授权”“Binder 已死亡”和“当前版本不兼容”。
- 权限请求必须由明确的用户操作触发；拒绝后不得循环请求。
- Binder 死亡或权限撤销时立即停止新任务，并让运行中任务进入失败/恢复流程。
- 必须按 shell UID 的真实权限逐项探测能力。Shizuku 已授权但无权写某个 sysfs 节点时，该 capability 显示“不支持”，不得误报为后端整体可写。
- 覆盖：Shizuku 未安装、服务停止、授权允许/拒绝/撤销、Binder 重连、可读但不可写、写入成功、读回不一致和恢复路径。

## 4. 后端能力矩阵

| 能力 | Dry-run | ADB 进程 | Root | Shizuku |
| --- | --- | --- | --- | --- |
| 变更预览 | 必须支持 | 必须支持 | 必须支持 | 必须支持 |
| 设备状态只读 | 模拟 | 当前仅桌面传输可用 | 固定特权只读模板已接入，待逐项真机验收 | 固定特权只读模板已接入，待逐项真机验收 |
| CPU/swappiness 写入 | 禁止 | 默认禁止 | CPU governor/频率与 swappiness 已进入白名单，ZRAM 禁止；待真机逐项开放 | CPU governor/频率与 swappiness 已进入白名单，ZRAM 禁止；仅 shell UID 实际可写时生效 |
| 快照与恢复 | 不改变系统 | 不用于第一版写入 | 必须通过 | 对已开放能力必须通过 |
| 任意 shell | 禁止 | 禁止 | 禁止 | 禁止 |

daemon 后端不进入第一版；未来只有在完成身份认证、协议版本、最小权限、断线和升级策略后才重新评估。

## 5. 场景恢复生命周期

场景运行状态至少包含：`Idle → Snapshotting → Applying → Active → Restoring → Idle`，任一步失败进入带原因的 `Failed`，且日志能关联原应用任务与恢复任务。

以下事件必须有确定行为：

| 事件 | 预期行为 |
| --- | --- |
| 进入匹配应用 | 仅在场景变化时创建一次原始快照，应用并读回验证 |
| 同一应用重复轮询 | 不重复写入，不覆盖原始快照 |
| 从场景 A 切换到场景 B | 串行处理；先安全恢复 A，再为 B 建立新快照并应用 |
| 离开所有匹配应用 | 自动恢复当前场景的原始值并读回验证 |
| 用户停用场景或手动停止服务 | 若场景处于 Active，先恢复再停止；恢复失败必须明确告警 |
| Activity 重建或重新进入总览 | 从持久服务状态恢复显示，不得把仍存活的服务误报为“未启动” |
| Usage Stats 权限撤销 | 不再触发新场景；若无法判断前台状态，执行保守恢复 |
| 后端失效或授权撤销 | 停止新写入并尝试使用原后端恢复；无法恢复时保留恢复记录和醒目告警 |
| 应用进程被系统杀死后重启 | 从持久化恢复日志识别未结束事务，先核对当前值，再恢复或提示用户处理 |
| 设备重启 | 不盲目重放旧写入；重新探测系统状态，并关闭已失效的恢复记录 |

恢复操作必须幂等：重复调用不会把值写成新的异常状态。恢复成功前不得删除快照；部分恢复必须保留未恢复项及失败原因。

## 6. 真机验证门槛

### 6.1 最小设备矩阵

- Android 6（minSdk 边界）：基础 UI、应用列表、Usage Stats 降级；FrameMetrics 明确显示不支持。
- Android 7 或 8：当前窗口 FrameMetrics、前台服务、场景轮询。
- Android 11：包可见性、后台限制、Shizuku 权限流程。
- Android 14 或 15：前台服务、通知权限/限制、Usage Stats、Root/Shizuku 当前行为。
- 至少覆盖两种厂商系统和一台接近 AOSP 的设备；CPU governor/频率与 swappiness 写入必须在实际支持对应节点的设备上执行，ZRAM 仅做只读验收。

### 6.2 必测路径

1. 首次安装且不授权：所有页面可浏览，不崩溃、不弹 Root/Shizuku 请求，写入控件保持关闭。
2. Usage Stats 允许、拒绝和撤销：服务状态与提示正确，无权限时不持续轮询。
3. Root 和 Shizuku 分别执行完整的授权、能力探测、预览、应用、读回、离场恢复流程。
4. 注入命令中途失败、读回不一致、服务停止、后端断开和进程重启，核对恢复及日志。
5. M8 连续采集至少 30 分钟：页面离开和停止后 listener/线程释放；session、摘要、CSV 一致；前台交互无明显卡顿。
6. Compose UI 用例在至少一个 API 23–25 设备和一个 API 34–35 设备实际运行通过。

### 6.3 通过条件

- P0 路径无崩溃、ANR、静默失败或未提示的部分写入。
- 所有写入都有变更前值、目标值、实际读回值和恢复结果记录。
- 不支持的设备明确显示原因，且不会出现可点击的危险写入控件。
- 连续场景切换、服务停止、权限撤销和进程重启后，系统状态可恢复或存在明确、可操作的未恢复告警。
- 测试记录包含设备型号、系统版本、后端版本、能力矩阵、结果和相关日志，不以“代码已构建”替代真机结论。

## 7. UI 与危险操作验收

### 7.1 五栏架构

- 底部导航固定为“总览、应用、场景、调节、监控”，M4 CPU 与 M5 内存/ZRAM 合并在“调节”内，不再建立第六个顶层入口。
- 任一顶层入口最多一次点击可达；当前选中项同时具有语义和视觉反馈，不能只靠颜色区分。
- “应用 → 场景”必须携带所选包名；“总览 → 场景/调节”必须直接到达目标任务，不返回旧式模块菜单。
- 在小屏和 200% 字体下，五栏名称、核心内容和主要操作不得重叠或不可达。

### 7.2 高风险确认

真实特权写入必须经过“编辑目标 → 变更预览 → 二次确认 → 执行 → 读回结果”五个可观察阶段。确认界面至少显示：

- 当前实际后端和授权状态。
- 每项能力的原值、目标值和作用范围。
- 自动恢复的触发条件；无法自动恢复时的明确警告。
- 快照、能力预检和恢复命令是否就绪。

快照不完整、能力未验证、后端已失效或已有事务执行中时，“确认并应用”必须禁用。执行期间不得重复提交。失败结果必须区分“未产生写入”“已自动恢复”“部分恢复失败”，并提供任务记录入口。

保存场景草稿、筛选应用、查看日志和 dry-run 预览不得使用高风险确认文案。ZRAM 重建与任意 shell 始终不可通过确认框绕过白名单。

### 7.3 可访问性

- TalkBack 可按标题、摘要、状态、主要操作的顺序完成五条核心用户路径。
- 触控目标不小于 `48 × 48 dp`，所有非装饰图标有内容描述，开关和页签能朗读选中状态。
- 状态不只依赖颜色；亮/暗主题的正文对比度至少 4.5:1。
- 200% 字体、小屏、横屏和系统动画关闭时，确认对话框与恢复告警仍可完整阅读和操作。
- UI 自动化至少覆盖五栏导航、应用到场景的上下文跳转、高风险确认禁用条件、防重复提交和失败/恢复三种结果文案。
