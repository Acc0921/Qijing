## 已确认的实现变化

- M2 不再只传包名：应用页展示真实图标与完整信息，并把完整 `AppEntry` 上下文交给 M3。
- M3 不再是旧式参数表单：链路工作台已把应用、意图、优先级、预演和启用组织为明确步骤。
- `SceneEngine.prepare` 与真实应用使用同一计划、白名单与快照来源，但不执行任何写入；预演通过不等于已生效。
- 场景保存默认不启用；真实启用前必须预演并经过高风险确认；相同应用的同优先级冲突会阻断启用。
- Root/Shizuku 已可执行特权快照读取，不能再描述为“仅普通 sysfs/proc 快照”；但真实写入尚未在真机执行。
- M4/M5 已具备手动安全调节用户链路，不能再描述为“只有只读状态和参数契约”。
- Compose UI 与持久服务状态契约已在 API 23 与 API 35 实际运行：8 项通过，Root-only 用例因模拟器条件跳过；不能再描述为“仅编译”。

## 当前发布阻塞项

1. **运行状态实时轨迹**：工作台尚未连续展示命中、快照、应用、读回、恢复和异常处理状态。
2. **跨进程恢复 journal**：正式场景尚未持久化原始快照与未完成事务，进程被杀后的恢复闭环未完成。
3. **真机真实写入**：Root/Shizuku 已有白名单、特权快照与读回代码，但尚未在明确授权的真机执行 CPU/swappiness 写入和恢复。

ZRAM 重建、任意 shell、daemon、外部应用 FPS 和旧数据迁移仍按第一版边界关闭，不作为上述三项完成度的替代目标。

## 后续实施顺序

1. 将场景运行状态流接入 `LiveHitCard`、`RecoveryLedger` 和链路时间线。
2. 持久化正式事务快照与恢复状态，完成杀进程/重启后的安全恢复测试。
3. 在用户逐项确认原值、目标值、命令、恢复命令和风险后，执行 Root/Shizuku 真机真实写入矩阵。

验收口径见 [后端与恢复验收标准](backend-acceptance.md) 和 [方案 A：场景链路工作台](scene-chain-workbench.md)。
